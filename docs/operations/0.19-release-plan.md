# 0.19 release plan

This release implements the 24 October 2026 review in dependency order. Source changes are developed on `feature/omada-0.19-reliability` from `develop`. The running 0.18 installation is separate.

1. **Reliability:** serialize request pacing, coalesce authentication, recover site discovery, classify retries, validate response envelopes and complete pagination, fix client identity resolution.
2. **Mutation policy:** preview by default, common audit/result semantics, separate recovery capability, validate configuration before preview/apply, redact secrets consistently.
3. **Verified controls:** semantic read-after-write verification, typed radio and SSID updates, explicit bounded switch-port workflows. Every new route must exist in the checked-in official API specification.
4. **Usability:** searchable enabled-tool catalog, optional compact dispatch through existing validators, legacy alias controls, accurate annotations, Wi-Fi/logging/camera diagnostic composition and completeness metadata.
5. **Maintenance:** private CA trust, remove duplicate implementation, synchronize documentation and inventory, dependency security updates, investigate issue #11 and account for existing PR #10.
6. **Validation and delivery:** lint, type checking, build, coverage, manifest/docs checks, protocol/HTTP contract tests, independent review, GitHub branch and PR with changelog and migration guide.

## Release gate

The repository requires write tools to be tested against a disposable lab controller before stable release. Unit and local HTTP contract tests do not satisfy that gate; adopted hardware is needed for radio/PoE behavior. Until evidence is recorded, use a release-candidate version and do not tag a stable release, move npm/Docker latest, or replace the production installation. Read-only smoke checks may use the existing controller; mutation checks use a lab only.

## Scope boundaries

Retain official Open API and stdio as the supported platform. Historical RF storage, autonomous retuning, private GUI compatibility, public HTTP hosting and arbitrary raw API execution are separate projects. Existing endpoint coverage is retained through canonical tools and documented legacy options. New diagnostics report missing evidence explicitly.

## GitHub intake

At initial inspection the repository had one open issue, #11 (anonymous Docker pull denied), and PRs #10 (redaction), #12 (beacon control), #13 (BLE device read). PR #10 is being incorporated with attribution. The other PRs remain separate contributions; endpoint overlap and resulting migration implications will be noted in release documentation.

## Completion and follow-on work

The 0.19 candidate covers priorities 1–5 above, with validation/publication evidence in [the validation record](0.19-validation.md). Hardware apply validation, the remaining Zod/Inspector major upgrades, RF history, configuration drift storage/review, certificate pinning and broader controller-family coverage remain explicit follow-on work. Source is independently implemented against the checked-in official specs; PR #10 is credited in the changelog and validation record.
